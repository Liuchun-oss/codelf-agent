# Codelf 定时任务（Scheduled Tasks）功能策划书

> 版本：v2（按真实代码核对订正）　|　日期：2026-06-26

## 一、背景与目标

Codelf 目前已打通微信远程通讯：用户在微信里发消息 → `ChannelManager` 接管 → 调用 `QueryEngine.submitTurn()` 跑一轮 agent → 结果翻译回微信。整条链路是**被动触发**的，必须有人发消息才会动。

本次目标是引入**主动触发**能力：让 codelf 能按时间规则（一次性 / 固定间隔 / cron 表达式）自动唤起 agent 执行任务，并把结果推送到微信或桌面 UI。典型场景：

- 每天早上 9 点自动汇总昨天的代码改动并发到微信
- 每隔 30 分钟检查某个服务/接口状态，异常时通知机主
- 指定时间执行一次性任务（如"今晚 8 点提醒我提交周报"）
- 定时跑测试 / 拉取数据 / 生成报告

## 二、可行性分析（openclaw 对照）

对照 `D:\openclaw-main` 的 cron 子系统，它工程化程度很高，核心经验完全可以借鉴：

| 维度 | openclaw 的做法 | Codelf 的落地策略 |
|------|----------------|------------------|
| 调度引擎 | `croner` 库解析 cron + 单个 `setTimeout` 自驱动循环（每分钟至少醒一次防漂移） | 引入 `croner`（轻量、零依赖），复用同款单定时器循环思路 |
| 任务模型 | `at` / `every` / `cron` 三种调度方式 | 完全沿用这三种 |
| 执行动作 | 注入系统事件唤醒主会话 / 隔离会话跑一轮 agent | 复用 `getQueryEngine(sessionId).submitTurn()`，**用独立 sessionId 隔离** |
| 结果投递 | none / announce(发频道) / webhook | none / 微信通知 / 桌面 UI（webhook 二期） |
| 持久化 | 原子写 `jobs.json`，重启补跑错过的任务 | 照搬项目内 `videoTaskQueue.ts` 的原子写 + 启动恢复范式 |
| 健壮性 | 指数退避、瞬时重试、连续失败自动禁用、卡死清理 | 一期实现退避+失败禁用，其余二期 |
| 管理入口 | CLI / Agent工具 / RPC / Web UI | 桌面设置面板 UI + 可选 Agent 工具 |

**关键结论**：codelf 的 `videoTaskQueue.ts` 已经实现了「内存数组 + 原子持久化 + `Map<id, timer>` 轮询器 + `resumeVideoTasksOnStartup()` 启动恢复 + 完成后 `notifyWeixin()`」这一整套范式。定时任务本质上就是这套范式 + cron 调度计算，**复用度极高，不是从零开发**。

## 三、功能设计

### 3.1 任务调度方式（三选一）

- **at**：在指定绝对时间执行一次（执行后默认自动删除）
- **every**：固定毫秒间隔重复（如每 30 分钟）
- **cron**：标准 cron 表达式 + 时区（如 `0 9 * * *` 每天 9 点，时区 `Asia/Shanghai`）

### 3.2 执行动作

定时到点后，构造一个 `AiSendPayload` 喂给 agent，跑一轮完整对话：

- `message`：任务里配置的 prompt（如"汇总今天 git 改动并简要点评"）
- `sessionCwd`：任务绑定的工作区目录
- `permissionMode`：取值**只有 `'default' | 'acceptEdits'` 两种**（代码事实，无 `'readonly'`）。
  - 允许写的任务 → `'acceptEdits'`：引擎自动放行文件/普通命令（危险操作如敏感路径/系统路径仍被 `PermissionEngine` 硬拦），**不阻塞**。
  - 只读任务 → `'default'`：执行器必须主动应答所有交互事件（见 4.2），否则会卡死。

### 3.3 结果投递

- **none**：只跑，不通知（结果留在任务运行记录里）
- **weixin**：通过 `notifyWeixin(text)` / `notifyWeixinImage()` 推给微信机主
- **ui**：通过 `sendToRenderer` 推桌面 UI 的任务面板
- **webhook**（二期）：HTTP POST 到指定 URL

## 四、技术方案

### 4.1 数据结构（新建 `shared/scheduleTypes.ts`）

```typescript
export type ScheduleKind =
  | { kind: 'at'; at: number }                    // 绝对时间戳(ms)
  | { kind: 'every'; everyMs: number }            // 固定间隔
  | { kind: 'cron'; expr: string; tz?: string }   // cron 表达式 + 时区

export type DeliveryMode = 'none' | 'weixin' | 'ui'

export interface ScheduledTask {
  id: string
  name: string
  description?: string
  enabled: boolean
  deleteAfterRun?: boolean        // at 任务默认 true
  schedule: ScheduleKind
  prompt: string                  // 喂给 agent 的消息
  workspaceRoot?: string | null   // 任务工作区，null=纯对话；路径一律用 path.join 处理（跨平台）
  delivery: DeliveryMode
  // allowWrite=false → permissionMode:'default' + 自动拒绝所有写/命令交互（只读）
  // allowWrite=true  → permissionMode:'acceptEdits' 自动放行（危险操作仍被引擎硬拦）
  allowWrite: boolean
  createdAt: number
  updatedAt: number
  // 运行时状态
  nextRunAt?: number
  lastRunAt?: number
  running?: boolean               // 本次执行中标记，防止周期重叠
  lastStatus?: 'ok' | 'error' | 'running' | 'skipped'
  lastError?: string
  lastDeliveryStatus?: 'delivered' | 'failed' | 'skipped'  // 微信投递结果，失败可在 UI 标红
  consecutiveErrors?: number      // 连续失败计数，达阈值自动禁用
}
```

### 4.2 调度服务（新建 `electron/services/scheduleQueue.ts`）

照搬 `videoTaskQueue.ts` 范式，核心要素：

1. 内存数组 `tasks: ScheduledTask[]` + 原子写 `userData/scheduled-tasks.json`（位置用 `app.getPath('userData')`，跨平台一致）
2. 引入 `croner` 计算 `nextRunAt`（cron 类型）；`every`/`at` 直接算时间戳
3. **单个 `setTimeout` 调度循环**：每次找最近的 `nextRunAt`，延迟 clamp 到最大 60 秒（防时钟漂移），到点收集所有到期任务并发执行
4. `resumeSchedulesOnStartup()`：在 `main/index.ts` 启动序里调用（与 `resumeVideoTasksOnStartup()` 同位置），清除残留 `running` 标记、补跑错过的周期任务（带上限保护）、重算 `nextRunAt` 后启动循环
5. 执行函数 `executeTask(task)` —— **防弹版（绝不卡死，见第六章四层防御）**：

```typescript
const HARD_TIMEOUT_MS = 5 * 60 * 1000  // 单任务硬上限，到点强制熔断

async function executeTask(task: ScheduledTask): Promise<void> {
  if (task.running) { update(task.id, { lastStatus: 'skipped' }); return }
  update(task.id, { running: true, lastStatus: 'running' })

  const sessionId = `cron:${task.id}`
  const engine = getQueryEngine(sessionId)
  engine.clear(sessionId)  // 每次清空，防历史无限累加

  let timedOut = false
  // 层3：执行循环，主动应答所有已知交互事件
  const runLoop = (async (): Promise<string> => {
    let output = ''
    for await (const ev of engine.submitTurn({
      sessionId, turnId: randomUUID(), message: task.prompt,
      permissionMode: task.allowWrite ? 'acceptEdits' : 'default',
      sessionCwd: task.workspaceRoot ?? null,
    })) {
      if (ev.type === 'text_delta') output += ev.content
      else if (ev.type === 'permission_request') engine.resolvePermission(ev.requestId, 'deny')
      else if (ev.type === 'file_change_proposed') engine.resolveFileChange(ev.changeId, 'reject')
      else if (ev.type === 'user_question') engine.resolveUserQuestion(ev.requestId, { answer: '', cancelled: true })
      // 任何未知的未来事件若也会阻塞 → 由层1看门狗 cancel() 兜底结算
    }
    return output
  })()
  runLoop.catch(() => {})  // 吞掉超时后孤儿 Promise 的迟到 rejection

  // 层1：硬看门狗 —— engine.cancel() 同时 abort 信号 + 结算所有 broker
  let watchdog: ReturnType<typeof setTimeout> | undefined
  const timeout = new Promise<null>((resolve) => {
    watchdog = setTimeout(() => { timedOut = true; try { engine.cancel(sessionId) } catch {} ; resolve(null) }, HARD_TIMEOUT_MS)
  })

  let output: string | null = null
  let err: unknown = null
  try {
    output = await Promise.race([runLoop, timeout])  // 层2：调度器永不被单任务阻塞
  } catch (e) { err = e } finally {
    if (watchdog) clearTimeout(watchdog)
  }

  // 结算状态（幂等清 running）
  if (timedOut || err) {
    const n = (task.consecutiveErrors ?? 0) + 1
    update(task.id, {
      running: false, lastStatus: 'error', lastRunAt: Date.now(),
      lastError: timedOut ? `执行超时（>${HARD_TIMEOUT_MS / 1000}s）已强制熔断` : String(err),
      consecutiveErrors: n, ...(n >= 3 ? { enabled: false } : {}),
    })
    if (n >= 3) void notifyWeixin(`⏰ 定时任务「${task.name}」连续失败 ${n} 次，已自动停用。`)
  } else {
    let deliveryStatus: 'delivered' | 'failed' | 'skipped' = 'skipped'
    if (task.delivery === 'weixin') deliveryStatus = (await notifyWeixin(output ?? '')) ? 'delivered' : 'failed'
    else if (task.delivery === 'ui') { sendToRenderer('schedule:taskOutput', { id: task.id, output }); deliveryStatus = 'delivered' }
    update(task.id, {
      running: false, lastStatus: 'ok', lastRunAt: Date.now(),
      lastDeliveryStatus: deliveryStatus, consecutiveErrors: 0, lastError: undefined,
    })
  }
  try { disposeQueryEngine(sessionId) } catch {}  // 必清理，下次重建干净引擎
}
```

> 调度循环对每个到期任务用 `void executeTask(task)` **fire-and-forget**，不 `await`，派发后立即按 `nextRunAt` 重排定时器——单任务无论发生什么都影响不到调度器本身。

## 五、安全设计（重点）

定时任务是**无人值守自动调用 agent**，agent 有写文件、跑命令的能力，这是最大风险点。必须做到：

1. **权限模型对齐真实代码**：`permissionMode` 只有 `'default' | 'acceptEdits'`。
   - `allowWrite=true` → `'acceptEdits'`：自动放行文件/普通命令；但 `PermissionEngine.decide()` 仍会**硬拦敏感路径、系统路径、引用敏感文件的命令**（`engine.ts:39-48`），这层保护无法绕过。
   - `allowWrite=false`（默认）→ `'default'` + 执行器自动拒绝所有写/命令交互，等价于只读。
2. **必须主动应答交互事件**：`default` 模式下 agent 写文件/跑命令会发出 `permission_request` / `file_change_proposed` / `user_question` 并**阻塞等待应答**。无人值守时执行器必须主动 `resolvePermission(deny)` / `resolveFileChange('reject')` / `resolveUserQuestion({answer:'',cancelled:true})`，否则 `for await` 循环**永久卡死、定时器泄漏**。（⚠️ 这是 v1 草案的严重漏洞，已修正）
3. **会话隔离 + 每次清空**：用 `cron:<taskId>` 独立 sessionId，不抢占微信实时会话；且因 `getQueryEngine` 返回常驻引擎，周期任务每次执行前 `engine.clear()`、执行后 `disposeQueryEngine()`，否则历史无限累加导致上下文爆炸。（⚠️ 同为 v1 漏洞，已修正）
4. **失败熔断**：连续失败达阈值（如 3 次）自动 `enabled=false` 并通知机主，避免坏任务反复触发。
5. **投递不可静默丢失**：`notifyWeixin()` 在未登录/未启用时静默返回 `false`，必须把返回值记入 `lastDeliveryStatus`，投递失败在 UI 标红。
6. **频率下限**：`every` 间隔设最小值（如 ≥60 秒），防止误配置导致高频空转。
7. **运行重叠保护**：单次执行超过调度间隔时，用 `running` 标记跳过本次（标记为 `skipped`）。

## 五之二、绝不卡死保证（最高优先级）

> 硬性要求：定时任务调度器**在任何情况下都不能被单个任务挂死**，哪怕一丝概率都不行。

### 代码层依据（已核对真实源码）

agent 运行中唯一会"阻塞等待"的地方是三个 broker：`PermissionBroker` / `FileChangeBroker` / `UserQuestionBroker`。三者的 `wait()` 都接收 `AbortSignal`，信号 abort 时**立即用安全默认值结算**（deny / reject / `{cancelled:true}`），见 `broker.ts:9-14`、`fileChangeBroker.ts:21-38`、`userQuestionBroker.ts:9-14`。

而 `QueryEngine.cancel()`（`queryEngine.ts:280-286`）会**同时**做两件事：`this.active.abort()` + 对三个 broker 调用 `cancelAll()`。因此：

> **`engine.cancel()` 是万能熔断点**：调用一次，所有正在阻塞的 broker 全部立即安全结算，generator 随之解开。它不依赖我们逐一识别事件类型——哪怕未来新增某种会阻塞的事件，cancel 也能一锅端。这是"绝不卡死"的硬基础。

### 四层防御（互相独立，任一层都能兜底）

| 层 | 机制 | 作用 |
|----|------|------|
| **层1 硬看门狗** | 每任务 `setTimeout(HARD_TIMEOUT_MS)` 到点强制 `engine.cancel()` | 终极保证：无论卡在哪，到点必被熔断 |
| **层2 Promise.race** | 执行循环与超时 `Promise.race` | 即使 generator 在 abort 后仍不返回，race 也走超时分支返回，**调度器永不被单任务阻塞**；孤儿 Promise 由 `.catch(()=>{})` 吞掉并与系统脱钩 |
| **层3 主动应答** | 循环内主动 deny/reject/cancel 所有已知交互事件 | 正常路径下根本不触发阻塞，看门狗只是保险 |
| **层4 调度器 fire-and-forget** | `void executeTask(task)` 不 await，派发后立即重排定时器 | 单任务的任何行为都隔离在调度器之外 |

### 不变量（实现时必须满足）

- 调度主循环（`armTimer`/`onTimer`）里**绝不出现 `await executeTask(...)`**，只能 `void executeTask(...)`。
- `executeTask` 内**唯一的无限/长等待**只有 `engine.submitTurn` 的 `for await`，且它被层1+层2双重包裹。
- `running` 标记与 `disposeQueryEngine()` 在**所有出口**（成功/异常/超时）都被幂等清理（放在 `finally` 等价位置），保证超时任务下次仍能正常调度。
- `HARD_TIMEOUT_MS` 必须**大于** agent 单轮合理耗时（建议 5 分钟），避免误杀正常长任务；同时**远小于** 调度间隔下限思考，避免超时任务与下一轮重叠（配合 `running` 标记双保险）。
- 进程重启后 `resumeSchedulesOnStartup` 必须先**清掉所有残留 `running=true`**（上次崩溃遗留），否则任务会被误判为"正在运行"而永久跳过。

| **调度器被单任务挂死（最高优先级）** | 四层防御：硬看门狗 `engine.cancel()` + `Promise.race` + 主动应答 + `void` fire-and-forget。`engine.cancel()` 为万能熔断点，绝不卡死 |
| 复用引擎致历史无限膨胀（v1 漏洞） | 每次执行前 `engine.clear()`、执行后 `disposeQueryEngine()` |

## 八之二、Mac 兼容性

结论：**Mac 端完全兼容，无需特殊改动**。依据：

- 持久化用 `app.getPath('userData')`（`videoTaskQueue.ts` 已验证），Mac/Win 各自指向正确的用户目录。
- 调度用 `setTimeout`/`setInterval`，跨平台行为一致。
- 新增依赖 `croner` 是**纯 JS、零原生编译**，不像 `better-sqlite3`/`node-pty` 需按平台 rebuild，**不给 Mac 打包增加任何原生编译负担**。
- 启动恢复挂在 `app.whenReady()` 中，与 `resumeVideoTasksOnStartup()` 同位置，和平台无关。`electron/main/index.ts` 已有的平台分支（`win32` 标题栏、非 `darwin` 退出）不受影响。
- 唯一注意点：任务 `workspaceRoot` 路径一律用 `path.join` 拼接，不硬编码 `\` 或 `/`。

## 九、决策定档（2026-06-26）

| 决策项 | 结论 | 说明 |
|--------|------|------|
| 开发范围 | **一期 + 二期一起做** | 含退避重试、运行历史、webhook、Agent 工具 |
| 权限策略 | **full_auto（完全放开）+ 单任务只读开关兜底** | 任务级 `allowWrite` 开关：开=`acceptEdits` 自动放行（敏感/系统路径仍被引擎硬拦），关=`default`+自动拒绝全部交互（只读）。无全局 `'readonly'` 模式 |
| 会话隔离 | **独立会话 `cron:<taskId>`** | 不污染微信实时对话历史 |
| 结果投递 | **微信（推送给机主）** | UI / webhook 作为二期可选项保留 |
| Agent 工具 | **二期做** | 让 AI 在微信对话里直接创建定时任务 |

> ⚠️ **full_auto 风险提示**：选择完全放开后，定时任务在无人确认时会自动执行 agent 的所有工具调用，包括删除文件、执行 shell 命令等破坏性操作。建议至少保留「单任务级别的只读开关」，对不信任的 prompt 单独限制；后续若改主意可随时收紧为 default 模式。
